Expression conditions

Proposal: hazard and UCA conditions become small typed expressions. Conditions are still grouped TLA+-style — a list of lines, each introduced by ∧ or ∨, nesting by indentation instead of parentheses — and that same layout is used for reading, text editing, structured editing and trace verdicts.

1 · How a condition reads

Rendered everywhere (UCA context, hazard condition, tables, docx/xlsx). The symbol sits in a fixed column, so nested lists line up on the content column exactly as in TLA+.

The same, as text

∧ Train speed > 0 ∧ ∨ ∧ Door state = closed ∧ Platform side ≠ left ∨ Emergency brake = applied ∧ Gap − 2 × Speed < 5 m ∧ ¬ Door state = prev(Door state)

Rule: a line that starts with ∧/∨ opens a list item; further ∧/∨ on the same line, or lines indented to that column, belong to the same item. Typed in ASCII (/\, \/, ~, and/or/not) they are rewritten on blur.

Both sides of a comparison must have the same type (same named symbolic type, same unit). Errors are shown in the editor and as validation findings; a text-only project never sees any of this.

6 · Model and code impact

Model

  • Cond = All | Any | Not | Cmp | Time | Event | Text; Cmp {left, op, right} over Expr = Const | Var | Prev | Call | Bin. Replaces Condition + Group; no migration, examples regenerated.
  • Printer ↔ parser (model/expr.ts), the text layout above is its canonical output.
  • Evaluator stays three-valued, with a per-line verdict tree for traces.

Open points

  • Refinement: expand only substitutes comparisons of a refined variable with a constant; arithmetic over a refined variable is left as is and flagged info.
  • Args on control-action parameters could use the same expressions (delay ≤ 2 × timeout); proposal: yes, second step.
  • Quantifiers over instances: not in this step.
  • Phasing: (1) Expr + evaluator + printer, (2) text editor, (3) rows editor, (4) trace verdicts, (5) refinement / MCP.
